## 0. 一页看懂（RW 只想看三行时看这里）

1. **结算发生在"触发帧"边界（每 0.2s = 20cs 一次）**，但时间按 1cs（0.01s）逐帧推进；一局最多 18000 个全局帧 / 900 个触发帧。

## 1. 本文为什么存在

框架设计 §4/§5 是 **v0.19 的设计稿**，而引擎已经按 P0.6 的修法走过一轮实现，两者在若干处**已经不一致**。本文把"引擎实际行为"逐条钉死，作为后续所有改动（光环、新原语、时机词补齐）的唯一基准。

**写这份文档的起因**：光环机制要写进 YAML 模板和引擎，但光环会同时触碰"持续施加""条件系统""状态存储"三条主线，必须先有一份能看懂的结算说明，再动代码。

| 项 | 框架设计 v0.19 | 引擎实况 | 处置 |

## 2. 确定性契约（不可违背）

1. **给定同一 `BattleOptions`（seed + 双方摆盘 + 双方技能），战斗的每一帧状态与全部日志逐字节一致。**
2. 引擎内**唯一**随机入口是 `BattleState.rng`（[engine/rng.ts](engine/rng.ts) 的 `Rng`）。禁止 `Math.random()` / `Date.now()` / `new Date()`（AGENT.md §5.4 红线）。
3. 所有遍历顺序必须是**显式排序结果**，不得依赖对象键顺序。当前所有"按来源排序"都落到 `loadOrder`（`createBattleState` 里"先 sideA 从左到右、再 sideB"，技能从 `SKILL_LOAD_ORDER_BASE` 起）。
4. 时间量一律整数 **cs**（1cs = 0.01s）。唯一允许小数的累加器是 `DotInstance.stacks`（灼烧指数衰减），且只在**对外读取**时取整（`Math.round`）。

## 3. 两级时钟（已实现的口径）

| 时钟 | 常量 | 值 | 作用 |
|------|------|----|------|
| 全局帧 | `GLOBAL_FRAME_CS` | 1cs = 0.01s | **唯一推进步长**。持续效果周期、卡牌状态计时、行动条、buff 时长都按它走 |
| 触发帧 | `TRIGGER_FRAME_CS` | 20cs = 0.2s | **结算边界**。只决定三件事：满条主动行动、被动/技能收集、胜负兜底 |
| 上限 | `MAX_TIME_CS` | 18000（180.00s） | 到达即超时判平局（`winner = sideA`、`draw = true`） |

## 4. 主循环（引擎实况）

### 4.1 初始化（`runBattle` 开头，`triggerFrame = 0`）

1. `validateBattleInput` → 逐侧 `buildBoardCards`（摆盘合法性在 `engine/board.ts` 校验，错误码 `E_SLOT` / `E_CARD_REF`）。
2. **广播 `battleStart`** → `collectPassives(state, queue, 'battleStart')` → `collectSkills(...)` → `drainQueue`。
3. `queue.clearFrameEvents()`：清掉 `fired`，否则 `battleStart` 会被当成"本触发帧发生过的事件"再收一次。

### 4.2 每个全局帧（共 18000 次）

```
0a  推进 1cs：对每一侧依次执行
       advanceDots        → 灼烧/剧毒/再生周期结算（返回本帧真正发生的跳伤/回血）
       advanceCardStatuses→ 加速/减速/冰冻剩余时长 -1cs
       pruneCardStatuses  → 剩余 ≤ 0 的状态移除
       advanceActionBar   → 未失效且非纯被动卡 gaugeCs += 1cs
0b  因果点胜负判定：对本帧发生的每一条持续效果跳伤，立刻 checkOutcome；
      分出胜负 → queue.clear() 并直接结束整局（判定细则见 §6.4）
0c  若本 cs 是触发帧边界 → 执行 4.3
```

### 4.3 触发帧边界（`triggerFrame += 1` 之后）

TODO ：加载条满后直接入触发栈，或者想办法解决浪费帧问题，一个物品主动触发结束后下一帧就要开始走下一个主动条了，如果帧边界再结算，这个地方要调整。
```
1  收集"满条者"：
     遍历 [sideA, sideB] × 各自 board（按 slot 升序）
     条件：!destroyed && periodCs 有限 && gaugeCs >= periodCs
     映射成主动行动 → 按 comparePending 排序 → 依次 applyAll
     每张卡行动完成后【无条件】broadcast('afterAction')
       （卡上没有 kind: active 也算"用过这张卡"，见 §9.4）
   全部行动结算**之后**，才对**收集时刻的那批卡**统一 consumeActionBar
     （gaugeCs -= periodCs，下限 0；余量结转，避免高速卡丢帧）
2  触发收集（仅在 isDirty() 时执行）：
     for event of EVENT_WORDS（['battleStart','afterAction','onPlayerDamaged']）
       若 hasFired(event) → collectPassives(state, queue, event)
     collectSkills(state, queue, event => queue.hasFired(event))   ← 只调用一次
     drainQueue → 排空队列，结算顺序完全由队列排序决定
3  queue.clearFrameEvents()（清 fired 与 dirty，队列已在 drainQueue 排空）
4  checkOutcome 兜底
```

**结算过程中产生的新事件只记账、不放回本帧**：`broadcast` 只往 `fired` 里 `add`，而 `fired` 要到步骤 3 才清；但**收集**已经在步骤 2 做过，所以本帧新广播的事件不会在本帧再触发一轮——它们留到下一个触发帧被收集。这一条与框架 §5「结算过程中产生的新事件并入下一个触发帧」一致。

**分帧粒度效应（重要）**：`afterAction` 在步骤 1 逐卡广播，但收集在步骤 2 才发生，于是**同一触发帧里多张卡行动，只算"`afterAction` 发生过一次"**（`fired` 是 `Set`）。这正好实现"同一触发器每触发帧至多结算一次"。

## 5. 触发器模型

### 5.1 三种来源与排序

| 来源 | `sourceKind` | `priority` | `loadOrder` | `tieBreak` |
|------|--------------|-----------|-------------|-----------|
| 卡牌被动 | `'passive'` | `ability.priority ?? 5`（1–10） | 卡的全局加载序（0 起） | `ability` 在 `abilities[]` 中的下标 |
| 技能 | `'skill'` | `skill.priority ?? 5` | `1_000_000 + 技能下标` | 技能下标 |
| 卡牌主动 | `'active'` | 恒 0 | 卡的全局加载序 | 0 |

排序函数 `comparePending`（[engine/tick.ts:211](engine/tick.ts#L211)）：**priority 降序 → loadOrder 升序 → tieBreak 升序**。
`SKILL_LOAD_ORDER_BASE = 1_000_000`（[engine/tick.ts:93](engine/tick.ts#L93)）保证**同优先级时技能后于一切卡牌被动**（规则 §6.2）。主动行动"行动条充满即结算"，不参与优先级比较。

> ⚠️ 代码注释笔误：[engine/state.ts:238](engine/state.ts#L238) 写"`SKILL_LOAD_ORDER_BASE`（1000）"，实际是 **1000000**。改注释即可，不影响行为。

### 5.2 条件判定的时机（易错点）

条件在**入队时**判定一次，用的是**入队那一刻的状态**，并把这份上下文随条目一起存下（`QueuedTrigger.context`）。因此：

- 条件为假 → 根本不入队；
- 条件为真 → 入队后**即使局面变化也不会重新判定**，动作照旧结算；
- 动作里的 `amount` 等表达式在**结算时**求值（`makeContext` 用最新状态重建），所以"条件看旧、数值看新"。

### 5.3 技能（本轮改定）

```ts
interface Skill {
  readonly id: string
  readonly name: string
  readonly version: number
  readonly priority?: number          // 缺省 5
  readonly description?: string
  readonly trigger?: { readonly event: string }   // 【选填】见下
  readonly stats: Readonly<Record<string, number>>
  readonly condition?: Condition
  readonly actions: readonly ActionSpec[]
}
```

**语义（用户 m00262 决议）**：

1. `trigger` **选填**。
2. 有 `trigger`：与卡牌被动**完全同语义**——只有本触发帧命中了该事件词才进入候选（如 `battleStart` 只在开局结算一次）。
3. 无 `trigger`：走"**每触发帧最多一次**"通道——每个触发帧边界都进入候选，但受队列去重与排序约束，一帧最多结算一次；**无 CD**。
4. 技能的 `loadOrder` 视为最低 → 同优先级时后于卡牌被动。
5. **纯光环技能不写 `trigger`**：光环的"持续施加"不走 `actions` 的一次性模型（见 §7）。

> **为什么改回选填**：P0.6 缺陷的根因是"收集逻辑按事件词逐个调用，而技能那段没有事件匹配"，导致一帧命中 N 个事件词就结算 N 次（实测 seed 42：三技能各 541 次、护盾涨到 10 万、双方锁血打满 180s）。当时的修法是把 `trigger` 改成必填（[engine/types.ts:124-145](engine/types.ts#L124-L145)），但那是**用类型强制**解决**收集路径**的问题。正确的解法是：把技能收集移出事件词循环（`collectSkills` 每帧只调用一次），再让 `trigger` 回到选填。本设计即按后者定稿。

### 5.4 当前会广播的事件词（只有 3 个）

`EVENT_WORDS = ['battleStart', 'afterAction', 'onPlayerDamaged']`（[engine/tick.ts:485](engine/tick.ts#L485)）。

| 事件词 | 广播点 | 触发条件 |
|--------|--------|----------|
| `battleStart` | 初始化 | 恒一次（不在触发帧循环里） |
| `afterAction` | 每张卡主动行动结算后 | **无条件**（卡上没有 `kind: active` 也广播） |
| `onPlayerDamaged` | `applyAll` 结束后 | 仅当本动作真有 `kind: 'damage' && amount > 0`；另在持续效果跳伤时广播 |

《时机表.md》B–E 类其余 18 词**均未实现**（`beforeAction` / `onCardDamaged` / `onShieldGained` / `onCardDestroyed` / `onBurnTick` …），差集见 §8.2。

## 6. 动作结算（八原语）

### 6.1 通用流程

`applyAll` → 逐条 `ActionSpec` → `applyAction`（[engine/primitives.ts:147](engine/primitives.ts#L147)）：

1. 选择器求值（`spec.target ?? 'self'`）→ `Selection { cards, players }`；
2. **先统一求值** `amount` / `seconds` / `duration`（`duration` 从秒换算成 cs）；
3. 按 `spec.do` 分发；`default` 分支用 `never` 穷尽检查，未知原语直接抛错。

### 6.2 各原语实际行为

| 原语 | 实际行为 | 关键细节 |
|------|----------|----------|
| `dealDamage` | 先护盾后血量，`shieldCostPerDamage = 1` | 对卡牌**只产生一条 `amount: 0` 的观测**（无实际损失）。伤害溢出被丢弃：`dealt = min(remaining, max(hp, 0))` |
| `healPlayer` | 不超 `maxHp`；**净治疗量 × 0.05** 同时扣灼烧与剧毒层数 | 层数扣减发生在回血之后；层数 < `DOT_MIN_STACKS`(0.01) 的 DOT 立即移除 |
| `shield` | 单一护盾池，`player.shield += amount` | 默认永久（无 `duration` 时无到期字段） |
| `gainStat` | **目标为玩家**：`stat ∈ {burn, poison, regen}` → 走 `applyDot`（同 kind 同 source 累加层数）；其它 stat 目前**只记日志不生效**（等角色 YAML）。**目标为卡牌**：找 `stat + source` 相同的 `StatModifier`，有则 `amount += amount`，无则 push | `source` = `context.self?.instanceId ?? 'skill'`；`stackLimit` **只在 push 时写入，现有条目的叠加不检查上限**（缺口，见 §8.4） |
| `applyStatus` | 对卡牌施加 `haste/slow/freeze` | 时长 = `duration ?? seconds`，换算成 cs；同类状态**取较大时长**刷新，异类并存（与框架 §4.6"三者互斥覆盖"**不同**——引擎是独立计时，符合规则 §18.8） |
| `charge` | `gaugeCs += seconds×100` | 不截断上限；冰冻 / 纯被动卡静默无效（`actionPeriodCs` 返回 `Infinity` 时直接 return） |
| `destroy` | `destroyed = true` | 无任何附加效果：不扣 buff、不清状态、不重置 gauge |
| `repair` | `destroyed = false` | **不重置 gauge**（框架 §7 写"gauge 从 0 重计"，引擎未实现 → §8.4） |

### 6.3 持续效果（引擎内置，不是卡面原语）

`advanceDots`（[engine/primitives.ts:380](engine/primitives.ts#L380)）**每全局帧**对每个 DOT：

```
nextTickCs -= 1
若 nextTickCs > 0 → 跳过
stacksRead = round(dot.stacks)          ← 只在算伤害/治疗时取整
  burn  : dealDamageToPlayer(player, stacksRead, 2) ; dot.stacks *= 0.8
  poison: dealDamageToPlayer(player, stacksRead, 0) ; 不衰减
  regen : healPlayerState(player, stacksRead)       ; 不衰减
nextTickCs += DOT_PERIOD_CS[kind]       ← 相位严格保持：
  burn 50cs(0.5s) / poison 100cs(1s) / regen 100cs(1s)
帧末：stacks < 0.01 的 DOT 移除
```

注意**灼烧衰减发生在造成伤害之后**，且 `stacks` 是小数（`0.8^n`）；因为内部保留小数，"1 层灼烧"会以 `1 → 0.8 → 0.64 …` 缓慢衰减，**不会一跳清零**，但持久的小数层数会长期留在状态里（这是刻意设计，规则 §14 的唯一豁免）。

## 6.4 胜负判定（因果点）

`checkOutcome`（[engine/tick.ts:221](engine/tick.ts#L221)）的规则：

| 情形 | 结果 |
|------|------|
| 任一方 `hp <= 0` | `finished = true`，对方获胜 |
| 双方同一判定点都为 0 | `draw = true`，`winner = 1`（平局判 sideA，规则 §3） |
| `timeCs >= 18000` 仍未分出 | 超时 `draw = true`，`winner = 1` |

**判定是因果点的、不是帧末的**（[engine/tick.ts:264-301](engine/tick.ts#L264-L301)）：`applyAll` 对**每一条 `ActionSpec`** 结算完就调一次 `checkOutcome`；一旦分出胜负立即 `queue.clear()`（丢弃本帧剩余触发器）并**中断当前动作组**里尚未执行的条目。持续效果跳伤同样在 `advanceDotsAndCheck` 里逐条判。

由此"双方同时归零"的实际含义是：**同一帧内、先结算的那条动作把 A 打到 0、同一动作组里更靠后的另一条动作（如对敌方玩家的反伤/连带伤害）又把 B 打到 0**——此时 `aDead && bDead` 同真，判平局。逐条判定保留了这种可能；若改成"整帧结算完再判"，先死的一方会被后续动作继续牵连，平局反而仍可能发生，但"立即结束"这条就更不成立。

这样做的语义理由（写在 [engine/tick.ts:3-15](engine/tick.ts#L3-L15)）：若只在帧末判，同一帧内已死的一方仍会继续结算卡牌、被动、技能与持续效果，与规则 §3"任一方 hp ≤ 0 → **立即**结束"直接矛盾。

## 7. 光环（aura）设计 —— 待拍板

> 这一节是**提案**，不是已实现内容。用户 m00262 要求"先完善卡牌和技能的光环机制，可以改动 YAML 模板"，但**看过本节并拍板前不动代码与 YAML**。

### 7.1 已定死的部分（待办 G9）

1. **卡牌或技能都可以施加光环**；
2. **只要卡牌在场 / 技能存在，光环就持续施加**；
3. **光环的效果数值独立于 `stats`，单独一个字段**。

### 7.2 提案：光环 = 每帧派生的只读修饰层

核心思路：**光环不写状态，只在读取数值时按规则派生**。理由：

- 光环是"持续施加"，若每帧真的去改 `stats`，退场时无法精确回滚（数值会被 buff、stackLimit、取整搅在一起）；
- 派生态天然满足"来源失效即消失"，无需退场钩子；
- 与既有 `effectiveStat` 的"基础值 + 修正之和"结构一致，只是多一层。

**提案结构（YAML）**：

```yaml
# 卡牌上（顶层字段，与 abilities 平级）
aura:
  appliesTo: [ownPlayer, ownCards]     # 复用选择器词表；[ownCards] / [ownPlayer] / 两者
  apply:
    - { stat: atk, amount: 2 }          # 对卡牌的数值修正
    - { stat: shieldPerSec, amount: 1 } # 对玩家的数值修正（玩家侧词表见 7.5）
  condition: { ... }                    # 选填：条件为假时光环不生效

# 技能上（顶层字段）
aura: { ... }                           # 同结构；纯光环技能不写 trigger
```

`appliesTo` 刻意复用选择器名而不是新造 `scope: own/enemy`，好处：① 与 `target` 同一套词表，玩家/DIY 只需记一套；② 天然支持"只对某类卡生效"的写法（7.4 的标签筛选器）；③ 将来要加"只对相邻卡生效"时不必再设计新机制。

**运行时（不落盘）**：

```
effectiveStat(card, stat)
  = card.stats[stat]
  + Σ CardStatModifier（buff / debuff）
  + Σ AuraContribution（由当前场上所有光环派生，每帧可重算）
```

`AuraContribution` 不入 `BoardCard.stats`，因此**不进日志、不被 stackLimit 影响、destroy/buff 清理不触碰它**。

### 7.3 需要解决的语义问题（逐条给建议）

| # | 问题 | 建议 | 理由 |
|---|------|------|------|
| A1 | 英文 id | 区块名 **`aura`**，数值块直接用 `apply: [{stat, amount}]` | `auraValue` 只够装一个数，装不下多属性；`apply` 与 `abilities.actions` 的直觉一致 |
| A2 | 是否占 `kind: active/passive` | **不占**。光环是**顶层字段**，与 `abilities` 平级 | 光环不挂行动条、不走触发器，塞进 `abilities` 会污染"主动/被动只由 cooldown 决定"这条规则 |
| A3 | 与 `enchant` 的关系 | `enchant` = 卡**自身**的常驻效果组（单槽、新覆盖旧）；`aura` = 对外**持续施加**的修饰层 | 两者作用对象不同，可共存 |
| A4 | 来源退场如何退场 | **不需要退场逻辑**（派生态）。判定"来源在场"= 卡 `!destroyed`；技能在场 = 技能已加载且其 `condition` 为真 | 避免引入框架里不存在的 `exit` 钩子 |
| A5 | 同一来源同一光环是否叠加 | 同一来源**不叠加**（同来源同 stat 取一次）；**不同来源线性相加** | 与 `gainStat` 的"同 stat 同 source 累加"不同——光环是持续值，不是层数 |
| A6 | 何时重算 | 在每个全局帧的 0a 之后（或按需在一次动作结算前），**不写状态** | 保证任何一帧的读数都一致 |
| A7 | 光环能否施加 DOT / 护盾这类**累积量** | **不能**。光环只允许"只读修饰"（`effectiveStat` 能看见的 stat）。要产生累积效果（每 0.2s +1 护盾）必须走触发器：`trigger: { event: tick }` 或新增时机词 | 累积量必须落状态，落状态就需要退场回滚，回到 7.2 想避开的问题 |
| A8 | 玩家侧光环怎么表达 | 卡牌侧复用 `effectiveStat`；**玩家侧需要新的"有效值"入口**（如 `shieldPerSec` / `damageTakenMul`），并明确它作用在哪一步 | 目前 `PlayerState` 只有 `hp / maxHp / shield / dots`，没有"玩家数值修正"容器（`gainStat` 对玩家的多数 stat 现在只记日志） |
| A9 | 光环是否影响 `cooldown` / 行动条 | **不允许**（作用在 `atk`/`speed` 之类可读数值上；`speed` 已在 `speedMultiplier` 里参与周期计算，若允许改 speed 需明确顺序） | 改行动周期会让"同一帧满条者集合"随光环变化，容易出难以复现的边界 |

### 7.4 标签筛选器（依赖待办 G13）

设计意图里有一类光环是"己方**武器**卡 +2 攻击"或"敌方**盾牌**卡减速"。`appliesTo` 用选择器名装不下"按标签筛选"，需要新增形态。两个候选：

```yaml
# 候选①：选择器里带筛选参数（新增词表项或参数化选择器）
appliesTo:
  - cards: { side: own, tags: [weapon] }

# 候选②：独立字段，与选择器并存
appliesTo: [ownCards]
filter: { tags: [weapon], hidden: false }
```

**建议候选①**：筛选是"选择器"的自然延伸，`{ count: <selector> }` 已有"选择器可参数化"的先例；候选②会引入"哪个字段先算"的隐含顺序。

### 7.5 光环的完整推演（三个场景）

**场景 1：卡牌光环（己方所有卡 +2 atk，来源在场）**

```
场上：A 的 cinder_wolf 带 aura { appliesTo: [ownCards], apply: [{stat: atk, amount: 2}] }
读取：effectiveStat(cinder_wolf, 'atk') = 10(基础) + 0(buff) + 2(光环) = 12
      effectiveStat(同侧另一张卡, 'atk') = 基础 + 2
来源被 destroy：下一帧派生态里该 +2 消失，被影响卡立即回到基础值
```

**场景 2：纯光环技能（无 trigger）**

```
技能 guardian_aura（stats 空、actions 空，只有 aura）→ 不写 trigger
每触发帧边界：collectSkills 看到它没有 trigger → 走"每帧最多一次"通道
但它的 aura 不产生任何动作结算，因此**不产生日志**；效果只体现在读数上
```

**场景 3：条件光环（己方血量 < 30% 时，己方卡 +5 atk）**

```
aura.condition: { cmp: lt, left: { ref: ownPlayer.hpPct }, right: 0.3 }
条件为假 → 派生态返回 0 贡献（不是"施加后移除"，是"从未生效"）
⇒ 血量在 30% 上下抖动时，攻击值会立刻跟着变，不留下任何残留
```

## 8. 缺口清单（本文档确认的"设计/实现不一致"）

### 8.1 条件系统装不下引用型比较（阻塞 G11）

`Expr`（[engine/types.ts:31-39](engine/types.ts#L31-L39)）与 `evaluateExpr`（[engine/expr.ts:153](engine/expr.ts#L153)）**只能产出 `number`**。因此 [参数表设计.md:81](参数表设计.md#L81) 的
`{ cmp: neq, left: { var: card }, right: { ref: self } }`（比较两张卡是不是同一张）与 [参数表设计.md:88](参数表设计.md#L88) 的 `target: { pick: self }` **都写不出来**。这条同时卡住光环的 `appliesTo` 与 §6.2 的 `afterAction` 类被动。

### 8.2 时机词差集

`EVENT_WORDS` 只有 3 词，而《时机表.md》B–E 类共 18 词标 ✅。若要落地光环相关的"每 0.2s 施加一次"或"目标离场时收尾"，至少需要：`beforeAction`、`onCardDamaged`、`onCardDestroyed`、`onCardRepaired`、`onShieldGained`、`onBurnTick` / `onPoisonTick` / `onRegenTick`。

### 8.3 规则说明书时间模型仍是单颗粒度

[规则说明书.md](规则说明书.md) §4 伪代码 / §5 / §6 仍写 `MAX_TICK = 900`、"每 tick = 0.2s"。引擎已经是 `MAX_TIME_CS = 18000`（1cs 步长）。这是**当前最大的文档风险**（待办 P0.6 已登记）。

### 8.4 其它确认到的实现缺口

| 位置 | 缺口 |
|------|------|
| [engine/primitives.ts:249-263](engine/primitives.ts#L249-L263) | `gainStat` 的 `stackLimit` 只在**新建**修正时写入，已有条目叠加时不检查上限（框架 §7 要求"达上限后替换最早一层并刷新时长"） |
| [engine/primitives.ts:336-350](engine/primitives.ts#L336-L350) | `repair` 不重置 `gaugeCs`（框架 §7 要求"gauge 从 0 重计"） |
| [engine/primitives.ts:133-140](engine/primitives.ts#L133-L140) | `applyCardStatus` 同类取**较大**时长刷新，框架 §7 写"三者互斥、后施加覆盖先施加"——两者不一致，需以规则说明书 §18.8 为准 |
| [engine/state.ts:238](engine/state.ts#L238) | 注释写 `SKILL_LOAD_ORDER_BASE`（1000），实际 1000000 |
| `gainStat` 对玩家的非 DOT stat（如 `maxHp`）| 只记日志、不生效（等角色 YAML 落地） |
