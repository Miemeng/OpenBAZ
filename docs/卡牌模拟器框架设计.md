# 异步自走棋卡牌模拟器 · 框架设计方案

> 版本：v0.21（**探针回收 + 本地 CI 基线 `npm run verify`（RW 决议 L0）**：骨架期两只临时探针 `engine/__probe__.ts` / `simulator/__probe__.ts` 与临时诊断脚本 `tools/diag-lint.mjs` 已回收，命令表 `probe:boundary` 行标记为已删除；`package.json` 新增 `verify` 串联六步基线（`check:config` → `typecheck` → `typecheck:client` → `lint` → `test` → 裸跑 `simulator/run.ts`），把 §2.5.3 第 5 条"CI 必须裸跑 CLI"固化成一条命令，**暂不接 GitHub Actions**。上一版 v0.20：移除普攻与基础行动，卡牌效果只有主动 / 被动；v0.19：时间模型明确为两级颗粒度 + 全局数值整数口径——全局时钟 0.01s / 触发器帧 0.2s 的作用范围与执行序、相位与帧边界约定，全局数值一律为整数、时间量以 cs 计、单次中间结果四舍五入即取整，唯一豁免为灼烧层数指数衰减）
> 技术栈：TypeScript + YAML，React + Vite（表现层）
> 目标：基于 YAML 热加载卡牌定义，支持玩家 DIY，确定性可复现的异步自走棋对战模拟

## 1. 设计原则

1. **确定性优先**：给定双方阵容 + 种子，战斗结果 100% 可复现。所有随机走唯一入口。
2. **引擎与表现分离**：战斗引擎为零依赖纯逻辑包，CLI 批量模拟与游戏客户端共用同一引擎；**同一份引擎源码同时支持两种宿主**——Node（CLI / 桌面）与浏览器（Web 客户端），两种宿主的差异只允许出现在 `cards/` 的适配层，不得进入 `engine/`（v0.13，见 §2.5）。
3. **玩家血量是胜负条件**：卡牌无血量，作为场上持续生效的"炮台/机关"存在；效果直接作用于对手玩家或己方卡牌。
4. **YAML 优先**：当前阶段只做 L2 结构化 YAML，暂不做 L1 卡面文字（见用户故事 2）；L1 编译器留待后期。
5. **词典驱动**：时机词 / 动作词 / 选择器均为封闭词典，解析失败即报错并给出建议。
6. **热加载**：卡牌文件保存即生效，加载失败不崩溃，进行中的对局不受影响。

## 2.5 仓库形态与运行边界（v0.13 决议）

### 2.5.1 仓库形态：单包，非 monorepo

**决议**：本仓库采用**单包（single package）**形态——一个 `package.json`、一份根 `tsconfig.json`、一个 `node_modules`，§3 的各目录是**模块边界**而非包边界。**不引入 pnpm workspace / monorepo。**

**理由**：

1. 单人开发、尚未开工 M1（《待办.md》§二），拆包的成本（tsconfig references、workspace 依赖协议、改 `engine/` 需先构建再被消费）立刻支付，而收益（多端并行发布、独立版本化）此刻兑现不了。
2. **包边界并不等于架构约束**：`packages/engine` 里同样可以 `import fs from 'node:fs'`，拦住它的是 lint 规则而不是文件夹。因此"拆包以保证引擎纯净"是伪收益——真正的机制是 §2.5.2 末的导入限制，单包里就能强制。
3. `packs/` `decks/` `skills/` `drafts/` 是**运行时数据**而非源码：在 monorepo 里无论单列 `packages/data` 还是留在仓库根，都会让其余包用相对路径往仓库外走，构建与打包都要额外处理。

**改判为 monorepo 的触发条件**（出现任意一条再拆；§3 的目录已按该边界生长，届时是搬目录而非重构）：

- `engine/` 需要发布为 npm 包或独立版本化；
- 出现多个独立发布的客户端（Web / Electron / 其他），需要各自产物与发布节奏；
- 多人并行开发，且需要 `engine/` 独立于应用锁定版本。

### 2.5.2 运行边界：Node 侧与浏览器侧

**两种宿主，同一份核心**：

| 职责 | Node 侧（CLI / 桌面） | 浏览器侧（Web 客户端） |
|------|----------------------|------------------------|
| 战斗模拟、tick 循环、触发器结算 | ✅ | ✅ |
| YAML 解析 → schema 校验 → 注册表 | ✅ | ✅（同一份纯逻辑） |
| 文件系统读取卡包 / 阵容 | ✅ `node:fs` | ❌ 无文件系统 |
| 目录监听热加载（`packs/**/*.yml`） | ✅（`node:fs.watch` / chokidar） | ❌ 无目录监听 |
| CLI、批量胜率、导出 | ✅ | ❌ |
| 卡牌数据来源 | 直接读工作区数据目录 | 由 Node 侧暴露的读取器 / 接口提供，**不得直接读盘** |

**推论 1（分层硬约束）**：`engine/` 与 `cards/` 的**纯逻辑部分**（`schema` / `registry` / `glossary` / `template`）必须同时能在 Node 与浏览器运行，因此它们内**不得出现 `node:*` 导入**。文件读写、YAML 文件加载管线、目录监听、CLI 输出一律留在 `cards/` 之外或 `cards` 的宿主适配层，**不得反向渗入 `engine/`**。

**推论 2（`packs/` 的定位）**：`packs/` `skills/` `drafts/` `decks/` 属于**工作区数据**，位于项目根层、不属于任何源代码模块，且在工作区**可读写**（热加载、草稿落盘）。客户端界面读取卡牌数据必须经 Node 侧中介（dev server 中间件 / 本地服务 / 预生成的清单产物），**不得假定前端能直接以静态资源方式访问这些目录**。打包发版时该目录的落点（用户数据目录 / 只读资源）另立决议，M5 之前不处理。

**推论 3（源码约束）**：`engine/` 与 `cards/` 不得使用 `.tsx`、DOM 类型、Vite 专属语法或 `import.meta.env` 等宿主相关 API——CLI 与 UI 共用这两层源码，宿主差异只能通过适配层注入。

**运行时与工具链（允许越出"零依赖"的范围）**：黄金法则 2 的"零依赖"**只约束 `engine/`**；`cards/`（loader / schema）、`simulator/`、`client/` 允许引入必要依赖。**当前已确定的依赖/工具链决策（v0.14）**：

| 项 | 决策 | 状态 |
|----|------|------|
| 表现层框架 | React + Vite | 已定；依赖已列（**尚缺 `@vitejs/plugin-react`，建 `vite.config.ts` 时补**） |
| YAML 解析 + schema 校验 | `js-yaml@5.4.2` + `zod@4.6.5`（或 ajv） | 已定并列入 `package.json`（`js-yaml` 自带类型，**不需要** `@types/js-yaml`） |

| Node 运行时 | **Active LTS 线**（Node 22.18+ / 24 / 26 均可）：类型擦除已 Stable，且 Vitest 5 的 engines 要求 `^22.12.0 \|\| ^24.0.0 \|\| >=26.0.0` | 已定并写入 `package.json` `engines`（配 `.npmrc` `engine-strict=true`）；RW 已卸载全局 TS 7 |

### 2.5.4 骨架落地实况（v0.15）

仓库根已建立单包骨架（**尚无任何业务源码**——`engine/` `cards/` `client/` `simulator/` 四个源码目录仅含 `.gitkeep`，数据目录 `packs/` `skills/` `drafts/` `decks/` 同样仅占位）：

| 文件 | 作用 |
|------|------|

| `.npmrc` / `.nvmrc` / `.editorconfig` / `.gitignore` | 钉版本与 engine 校验、Node 大版本提示、行尾与编码统一；`.gitignore` **明确不忽略 `packs/` `skills/` `drafts/` `decks/`**（它们是工作区数据，推论 2） |

### 2.5.5 零源码期的验收入口（v0.16 新立，v0.17 修正）

骨架期没有任何 `.ts` 文件，直接跑 `tsc --noEmit` 会**以错误退出**：`error TS18003: No inputs were found in config file '…tsconfig.json'`。这不是配置写错，而是 `tsc` 对"零输入"的既定行为——但后果是"基线全绿"在最需要它的那段时间里根本跑不起来。**处置办法不是把 `typecheck` 删掉或摆烂，而是补一个不依赖源码的配置层验收**：

| 命令 | 作用 | 零源码时 |
|------|------|----------|
| `npm run check:config` | 解析两份 tsconfig 并断言关键不变量（见下） | ✅ 有效——这正是零源码期该验的东西 |
| `npm run lint` | ESLint flat config 自身可解析、可应用 | ✅ 有效（无文件可检时退出码 0） |
| `npm run test` | Vitest 跑测试 | ✅ 有效（带 `--passWithNoTests`，见下） |
| `npm run typecheck` / `typecheck:client` | 逐项目类型检查 | ⏳ **零源码时必然失败**，等第一个 `.ts` 落地即恢复有效 |
| ~~`npm run probe:boundary`~~ | ~~`node engine/__probe__.ts`：验证类型擦除 + `import type` + ESLint 的 `engine/**` 规则块~~ → **v0.21 已删除**（证据已在 v0.18 取得，探针与脚本一并回收；两个反向用例今后只能按 AGENT.md §5.4 的步骤临时写一行再删） | — 已删除 |

**`check:config` 为什么不用 `tsc --showConfig`（v0.17 修正）**：`--showConfig` 同样会因零输入报 TS18003 并 exit 1，于是"配置有效"与"还没源码"两件事被混在一起——**它对 `tsconfig.client.json` 永远得不到有效结论**（`client/` 在骨架期只有 `.gitkeep`），等于假绿。现改为 `tools/check-config.mjs`：**只读 tsconfig、断言不变量、不开子进程**（本沙箱禁止管道 stdio，`spawnSync` + `encoding` 会直接 EPERM）。它检查的是：`noEmit` / `allowImportingTsExtensions` / `erasableSyntaxOnly` / `verbatimModuleSyntax` 四项齐备、**`paths` 绝不出现**、Node 侧 `types` 含 `node`、client 侧 `types` 为空且 `jsx: react-jsx`。等第一个 `.ts` 落地后 `typecheck` 恢复有效，该脚本即可删。

**三条随之而来的约定**：
1. **`typecheck` 不再用 `&&` 串联两个项目**：原写成 `tsc --noEmit && tsc -p tsconfig.client.json --noEmit`，**前一条失败会吞掉后一条的错误输出**（RW 实测正是如此：只看到 `tsconfig.json` 的 TS18003，client 侧结果未知）。现拆为 `typecheck` 与 `typecheck:client` 两条独立命令，串联与否交给调用方（CI）显式决定。
2. **`test` 带 `--passWithNoTests`**：Vitest 默认在"零测试文件"时以退出码 1 结束，会让骨架期的基线假红。该选项**只在没有测试文件时放宽**，一旦有测试文件，失败照旧失败——不构成掩盖。
3. **探针文件是临时的（v0.21 已回收）**：`simulator/__probe__.ts` 与 `engine/__probe__.ts` 曾只为让 `tsc` 有输入、让 ESLint 的 `engine/**` 块能被真实触发（探针里那句 `node:fs` 导入故意违规，靠 `eslint-disable` 才通过）。证据取得后**已于 v0.21 删除**（连同临时诊断脚本 `tools/diag-lint.mjs`；`simulator/__probe__.ts` 的职责由 `simulator/run.ts` 承担）——`engine/` 里出现 `node:*` 就是违规，不能留下。

**三条实现细节（踩过的坑）**：① `eslint.config.js` 的类型感知解析（`parserOptions.projectService`）**不是可选项**——`no-restricted-imports` 的 `allowTypeImports` 只在类型信息可用时生效，否则连合法的 `import type` 都会被拦，直接与 §2.5.2 的"仅允许 `import type`"冲突；② **宿主全局绝不能用"`globals` 置 `'off'` + `no-undef`"来拦**：`typescript-eslint` 的 recommended 已把 `no-undef` 对 `**/*.ts` 关掉（`@typescript-eslint/eslint-plugin/dist/configs/eslint-recommended-raw.js:36`），那种写法在骨架期看着有效、**一有真实源文件就一条都不报**；必须用 `no-restricted-globals`（支持 `{name,message}` 条目，另有 `globals`/`checkGlobalObject`/`globalObjects` 选项；只报运行时引用，故与 DOM 同名的类型注解不误报）。**这条是修正记录**：本文件 v0.17 的第一版曾把失败归因于"该规则条目只能是字符串"，属未读规则源码就下结论，且引入的假绿比原报错更有害，详见 AGENT.md §5.4；③ `package.json` 的 `build` 脚本目前**只是 `tsc --noEmit` 的别名**，因为引擎由 Node 直跑、确实可能不需要 emit——这正是待办 P0.5-4b 要定稿的事，定稿前不要把它当作真实构建。

**路径约定（已统一）**：文档目录已改名为 `docs/`，与 §3 及 AGENT.md §6 的引用一致（详见下方"路径约定（v0.16 已统一）"）。


**§3 中 `packs/` 等数据目录的读取方式，一律按本节的宿主边界理解。**

**依赖方向（单向，不得反向）**：`client → cards → engine`、`simulator → cards → engine`；`engine/` 不得导入任何其他层的**运行时值**。

| 导入方 → 被导入方 | 运行时值 | 仅 `import type` | 说明 |
|-------------------|----------|------------------|------|
| `engine` → `cards` | ❌ | ✅ | 引擎不得依赖卡牌加载层 |
| `engine` → `simulator` / `client` | ❌ | ❌ | 禁止任何形式 |
| `cards` 纯逻辑（schema / registry / glossary / template）→ `node:*` | ❌ | — | 保证浏览器宿主可运行 |
| `cards` loader（宿主适配层）→ `node:*` | ✅ | — | 文件 IO / 监听的唯一落点 |
| `client` → `engine` / `cards` | ✅ | ✅ | 表现层只消费引擎结果与日志 |

**强制机制**：以上表格在单包形态下**唯一有效的落点是仓库根 ESLint 的 `no-restricted-imports`（按 `engine/` / `cards/` 分 override 块）**，配合 `verbatimModuleSyntax`（或等价配置）保证 `import type` 在产物中真被擦除。执行细节与实施状态见《AGENT.md》§5.4。

**已确立：本节的架构约束靠 lint 规则强制，不靠包边界。** 任何"因为拆了包所以不会违规"的论证在本仓库不成立。

### 2.5.3 工具链决策依据与单一语法子集（v0.14 决议）

**决策**：Node 走 Active LTS 线（版本取自 §2.5.2 表）、TypeScript 用 `5.9.x`、测试框架用 Vitest 5、Vite `^8`。**判据是工具链确定性优先，不是速度优先**（RW 明确要求）。

**为什么不上 TypeScript 7（原生 Go 编译器）**：7.0 已于 2026-07-08 正式发布，官方给出 8–12× 加速与 6–26% 内存下降——但代价是原生版收窄了 JS API 面，官方公告明确"依赖特定全局声明的项目需要显式列出它们"。当前 `typescript-eslint` 的官方支持区间为 `>=4.8.4 <6.1.0`：**7.0 不在支持区间内**，需等 typescript-eslint v9 一类的联动到位。本项目单人开发、代码量小，7.0 省下的是**每次 typecheck 数秒**，而换来的是 lint / 编辑器 / 未来依赖的不确定性——不划算。生态全绿后再升，届时升级成本不会更高。

**为什么不是 6.x**：npm registry 中 `typescript@6.0.0`、`6.0.1` **均不存在**（404），只有 `6.0.0-beta`；尽管 6.0 公告已于 2026-03-23 发出，**正式版不可确证**。因此 5.9.x 是唯一"成熟且可得"的稳定线。

**为什么不选 `node:test`（内置、零依赖）**：`node:test` 是最贴近运行时的选择，但本项目**已经**要装 Vite；Vitest 5 复用 Vite 的解析与配置，不需要第二套构建认知，且 M6 的 React 组件测试可无缝接入。RW 选择"成熟一点"的框架，Vitest 是 Vite 生态里的既定答案。（`node:test` 仍是可接受的回退：它零依赖、且测试与 CLI 共用完全相同的运行时。）

**必须遵守的单一语法子集（本决策的硬约束）**：

引擎代码要同时对**三条链路**成立——`node` 原生类型擦除（跑 CLI）、Vitest/esbuild（跑测试）、`tsc`（只做类型检查）。**三条链路的语法能力取交集**，即"可擦除语法"：

1. **禁 `enum`、带运行时代码的 `namespace`、构造函数参数属性、装饰器、import 别名**（Node 擦除不支持；`--experimental-transform-types` 在 Node 26 已移除，没有转换退路）；
2. **源文件导入写 `.ts` 后缀 + 开 `allowImportingTsExtensions`**（Node ESM 强制要求扩展名；本仓库 `noEmit`，故用 `allowImportingTsExtensions` 而非官方推荐的 `rewriteRelativeImportExtensions`，理由见下方配置说明）；
3. **禁 `tsconfig` 的 `paths` 别名**——Node 不读 `tsconfig.json`，别名在 CLI 侧直接报错。替代方案：相对路径，或 package.json 的 `#` subpath imports（唯一不依赖 tsconfig 的别名机制）；
4. **开 `erasableSyntaxOnly`、`verbatimModuleSyntax`**：前者让违规在类型检查阶段就暴露，后者保证 `import type` 真被擦除（否则 Vitest 会"全绿"而 `node` 侧运行时报错）；
5. **验收不能只看测试**：CI 必须**真实跑一次 `node simulator/*.ts`**（哪怕小规模对局）。Vitest 通过 esbuild 转译，会容忍 Node 擦除不支持的语法——只有裸跑 CLI 才能证明"测试过了 = CLI 能跑"。

**对应 tsconfig（已落地，见 §2.5.4 的 `tsconfig.json`）**：

```json
{
  "compilerOptions": {
    "noEmit": true,                          // 引擎由 Node 直跑 *.ts，不产生产物
    "target": "esnext",
    "module": "nodenext",
    "allowImportingTsExtensions": true,      // 让 tsc 接受 './x.ts' 这种带后缀的导入
    "erasableSyntaxOnly": true,
    "verbatimModuleSyntax": true
  }
}
```

> Node 官方推荐里对应的一项是 `rewriteRelativeImportExtensions: true`，它解决的是"源码写 `.ts`、`tsc` 输出 `.js`"时的重写问题。**本仓库不 emit（`noEmit: true`），没有需要重写的产物**，故改用 `allowImportingTsExtensions` 让类型检查接受带 `.ts` 后缀的导入；两者都要求 `noEmit`（或 `emitDeclarationOnly`）才合法。若将来 `build` 真的产出 JS（待办 P0.5-4b），这一项要换回 `rewriteRelativeImportExtensions`。

补充两条 Node 侧硬事实（影响分层，不只是配置）：**`.tsx` 文件不被类型擦除支持**——这从运行时层面再次证明 `engine/` 与 `cards/` 纯逻辑中不得出现 JSX（与 §2.5.2 推论 3 一致），React 组件只能待在 `client/`；**`node_modules` 内的 `.ts` 一律拒绝**——所以任何依赖都必须以编译后的 JS 形式发布，`engine/` 零依赖这条纪律顺带免受第三方 TS 源码影响。另需注意 `@types/node` 会把 `process` / `Buffer` / `setTimeout` 等全局声明注入整个项目（含 `engine/`），**"引擎零 Node API"因此只能靠 §2.5.2 的 ESLint 规则守住，类型系统不会拦**。

## 4. 核心类型设计

### 4.1 卡牌定义（CardDef）

```typescript
interface CardDef {
  id: string;                 // 全局唯一
  version: number;            // 版本号，战斗日志记录用于追溯
  name: string;
  description?: string;       // 卡牌描述（设计风味，选填），小字显示在悬浮窗内
  cooldown: number;           // 冷却时间（秒，必填）：行动条充满周期 = cooldown × (cdp ÷ 100) ÷ 速度倍率；= -1 为纯被动物品（无行动条、不结算主动效果，规则 §5）
  owner?: string;             // 卡牌归属角色 id（规则 §17：模拟模式缺省归属本方默认角色 hero_default_a / hero_default_b）
  size: 'small' | 'medium' | 'large';
  slots: number;              // 占用格数，默认由 size 推导：小1 / 中2 / 大3（可覆盖）
  rarity: string;             // 品阶 id = 这张卡的最低品质，引用 rarities.yml（bronze/silver/gold/diamond 或自定义）
  frame?: string;             // 自定义卡框（图片资源 id），覆盖品阶默认卡框
  stats: {                    // 开放数值表：卡牌效果数值的唯一来源（规则 §8.2 书写规则）
    atk: number;              // 攻击数值：可被效果以 { ref: self.atk } 引用、可被 buff（**不内置普攻**，见 v0.20 决议）
    speed?: number;           // 行动条速度倍率，缺省 1（受加速×2 / 减速×0.5 / 冰冻=0 影响）
    [stat: string]: number;   // 自定义数值字段（约定：shd 护盾 / hel 治疗 / bur 燃烧 / poi 剧毒 / reg 再生
                             // / has 加速时长(s) / sol 减速时长(s) / fre 冰冻时长(s) / chg 充能时长(s)
                             // / cdp 冷却百分比系数（缺省 100，修正加算）），供 abilities / enchant
                             // 以 { ref: self.<stat> } 引用（读取含战斗内 buff 的实时值）
    // 卡牌无血量
  };
  multicast?: number;         // 多重触发，默认 1：行动条充满后主动行动的次数；>1 时卡面标注 *N、悬浮窗标明
  // 卡牌效果只有两种：kind: 'active'（行动条充满时按书写顺序结算）与 kind: 'passive'（由触发器时机驱动）。
  // 可以只有主动、或只有被动；不存在第三种"内置攻击 / 基础行动"（v0.20 决议，规则 §5）。
  // （已废除 baseAction / activeAction 主体效果自定义）
  buy_prize?: number;         // 买入价值；为空则从价值定义文件 card_values.yml 获取（规则 §16）
  prize?: number;             // 当前售价；缺省由价值定义文件获取；模拟模式战斗内不变价
  enchant?: Action[];         // 附魔常驻效果组（规则 18.7：单槽，新附魔覆盖旧的；每项为动作，见 3.4）
  tags?: string[];            // 种族 / 职业标签，供"每有一个X"类效果计数
  hidden_tags?: string[];     // 隐藏词条（不显示卡面，供逻辑用）
  abilities: Ability[];       // 见《YAML数据格式规范》§3；条目须带卡内唯一 id（v0.9，供 inherit_override 按 id 合并）
  inherit_override?: InheritOverride[];  // 品质继承覆盖（规则 §13.1）：从最低品阶下一阶到最高品阶每阶一段、必须齐全
}

// 品质继承覆盖段（挂在 CardDef.inherit_override；规则 §13.1 v0.9）
interface InheritOverride {
  rarity: string;             // 该段生效的品阶 id，须沿合成链递增
  stats?: Record<string, number>;  // 增量（delta，可正可负）：该品阶基础值 = 最低品阶基础值 + 沿途增量之和；
                                   // 只改卡面基础值，不触碰局外养成等运行时附加数值
  abilities?: AbilityOverride[];   // 按 id 合并覆盖；未列出的条目原样继承
  // 其余字段（cooldown / enchant / tags / 经济字段）不可覆盖，一律继承
}

// abilities 覆盖条目：condition 与 actions 全写，kind 沿用被覆盖条目
interface AbilityOverride {
  id: number;                 // 必须引用本卡 abilities 中已存在的条目 id
  condition?: Condition;      // 全写覆盖
  actions: Action[];          // 全写覆盖，至少 1 条
}
```

**品阶定义（packs/<pack_id>/rarities.yml，可扩展自定义；模板见《稀有度YAML模板.yml》）**：

```yaml
rarities:
  - { id: bronze,  name: 青铜, color: "#8d6e63" }
  - { id: silver,  name: 白银, color: "#b0bec5" }
  - { id: gold,    name: 黄金, color: "#ffc107" }
  - { id: diamond, name: 钻石, color: "#00e5ff", frame: diamond_frame }
  # 自定义示例：- { id: mythic, name: 传说, color: "#e040fb", frame: mythic_frame }

upgrade: [bronze, silver, gold, diamond]   # 二合一合成链（可扩展），见规则 §13
```

品阶 / 卡框只影响表现与卡包稀有度统计，不影响战斗逻辑（除非卡牌效果引用）。

**品质合成与继承（规则 §13）**：

- 合成关系在 `rarities.yml` 中定义，默认 `bronze → silver → gold → diamond`，低品质二合一获得高一阶品质卡牌；
- **模拟模式不体现合成**，后续完整模式实现；
- **品质继承**：高品质卡牌继承低品质卡牌的基础数值；有变化的效果单独书写、覆盖原有效果（覆盖写法见《YAML 数据格式规范》）。

### 4.2 场上卡牌（BoardCard）

```typescript
interface BoardCard {
  instanceId: number;         // 本场战斗唯一（同名卡可多张）
  cardId: string;
  cardVersion: number;
  side: 'A' | 'B';
  slot: number;               // 起始格（占用 slots 个连续格）
  buffs: Buff[];              // { stat, delta, source, expiryTick, stackCount }
  cardEffects: CardEffect[];  // 加速 / 减速 / 冰冻 等卡牌状态（见 4.6）
  destroyed: boolean;         // 被 destroy 失效（规则 9.7：失效 ≠ 离场，仍占位）；唯一复原方式是 repair（规则 9.8）
  actionGauge: number;        // 行动条进度
  actionCount: number;        // 主动行动已执行次数（everyN 主动效果的计数依据）
  queuedTriggers: number;     // 触发节流：本 tick 内超出一次的触发积累数，逐 tick 结算（见 5.1）
}
```

卡牌**无血量、不会因伤害死亡**；使卡牌失效的唯一方式是明确的效果 `destroy`（失效 ≠ 离场：卡牌仍占位在场上，不推进行动条、被动全部停用，挂着的 buff/debuff 数据保留），可由 `repair` 重置复原。

### 4.5 玩家技能（SkillDef）

技能**属于玩家（阵营）而不属于卡牌**。每名玩家可携带若干个技能，每个技能由**触发器 + 效果列表**组成，**无冷却、无费用**，只要触发器条件满足就结算。这正好呼应用户故事 1 中"技能以圆形显示，置于头像两侧"的表现形式。

```typescript
interface SkillDef {
  id: string;                 // 全局唯一
  version: number;
  name: string;
  icon?: string;              // 表现层图标资源 id
  stats?: {                   // 开放数值表（v0.10 新增）：技能效果数值的唯一来源，规则同 CardDef.stats（atk 非必填）
    [stat: string]: number;   // 自定义数值字段（约定同卡牌：shd / hel / bur / poi / reg / has / sol / fre / chg / cdp）
  };
  trigger: Trigger;           // 与卡牌 ability 共用同一套触发器机制（见 4.1）
  condition?: Condition;
  actions: Action[];          // 与卡牌共用同一套动作原语（见第 7 节）；数值型参数一律 { ref: self.<stat> } 引用本技能 stats（规则 §8.2）
  priority?: number;          // 触发优先级，缺省 5、范围 1–10（v0.10；与卡牌被动同台比较，见 5.1）
}

// 运行时
interface SkillInstance {
  skillId: string;
  side: 'A' | 'B';
  useCount: number;           // 统计/日志用，无机制含义（无 CD 故无冷却状态）
}
```

**与卡牌被动的区别**：技能不挂在任何卡上，没有"入场"概念，没有冷却；只要触发器满足即入栈结算。一张卡的被动与其携带者的技能可同时响应同一事件，按 5.1 的统一优先级规则排序：技能使用默认 `priority`，优先级相同时技能视为加载顺序最低，**技能后于卡牌被动结算**（规则 §6.2 / §12 v0.8 决议）。技能携带数量无上限。

### 4.6 持续效果与状态（规则说明书 §1 附录）

```typescript
// 玩家持续效果（挂在 PlayerState.effects；引擎以独立通道维护生命周期，规则 §18.9 v0.10）
interface StatusEffect {
  kind: 'burn' | 'poison' | 'regen';
  stacks: number;             // 层数 X（灼烧随跳伤衰减 20%，剧毒 / 再生不衰减）
  duration?: number;          // 持续 tick 数（缺省常驻，直至层数归零 / 被净化）
  source: string;             // 来源（instanceId / skillId），供"来源消失即移除"类联动
  enter?: Action[];           // 进入效果：施加时立即结算一次（选填）
  exit?: Action[];            // 退出效果：移除时结算一次（选填）
}

// 卡牌状态（挂在 BoardCard.cardEffects）
interface CardEffect {
  kind: 'haste' | 'slow' | 'freeze';
  expiryTick: number;         // 到期于 tick 边界移除
  source: string;
}

// 附魔为常驻效果组（挂在 CardDef.enchant；规则 18.7 v0.8 决议：一张卡同时至多一个生效附魔，新附魔覆盖旧的）
// 每项为动作（Action），结构与 Ability.actions 完全一致
```

| 效果 | 归属 | 规则（规则说明书 §1 附录） |
|------|------|------|
| 护盾 shield | 玩家 | 独立于血条，显示在血条上方；无特殊说明时攻击先作用于护盾；**抵御灼烧而不防御剧毒**；每点护盾可抵御 2 点灼烧伤害 |
| 治疗 heal | 玩家 | 恢复血量（不超 maxHp）；X 点治疗同时清除身上 0.05X 层灼烧与 0.05X 层剧毒 |
| 灼烧 burn | 玩家 | X 层灼烧每 0.5s 造成 X 点伤害；造成伤害后 X 减少 20%（衰减）；被护盾抵扣（2 伤/1 盾） |
| 剧毒 poison | 玩家 | X 层剧毒每 1s 造成 X 点伤害；**无视护盾、不衰减** |
| 再生 regen | 玩家 | X 层再生每 1s 恢复 X 点血量；不衰减 |
| 加速 haste | 卡牌 | 行动条速度翻倍；等效行动间隔最短不低于 1s |
| 减速 slow | 卡牌 | 行动条速度减半 |
| 冰冻 freeze | 卡牌 | 行动条速度为 0，且无法进行主动行动 |
| 充能 charge | 卡牌 | 行动条直接推进 X 秒；单次推进最多触发一次主动行动 |
| 摧毁 destroy | 卡牌 | 被摧毁卡牌在战斗中完全失效（见 4.2） |
| 修复 repair | 卡牌 | 重置被摧毁的卡牌 |
| 多重触发 multicast | 卡牌固有 | 默认 1；>1 需卡面标注 \*N、悬浮窗标明 |
| 附魔 enchant | 卡牌 | 常驻效果组（存在即生效），写在本卡设定文件中；单槽，新附魔覆盖旧的（规则 18.7 v0.8/v0.9 决议） |

**结算时刻**：灼烧 0.5s、剧毒/再生 1s，均走 0.01s 精度时间轴（与冷却同精度），在 tick 内的固定相位结算以保证确定性；具体相位见 5.0。

## 5. 战斗主循环（tick 制）

**时间模型**：两级颗粒度，见 §5.0——**全局时钟 0.01s**（一切计时的真相来源）+ **触发器帧 0.2s**（只约束触发器结算时机）。MAX_TICK = 180s（900 触发帧，规则 §14）；**全局数值一律为整数（时间量以 cs 计），舍入口径见 §5.0.2**。卡牌只有一行 10 格，"相邻" = 同侧格子索引相邻（无行列几何问题）。

```
初始化：按阵容摆盘 → 广播 battleStart → 按优先级结算触发栈
循环（触发帧 tick++，上限 MAX_TICK = 900）：
  0. 触发帧内推进 20 个全局帧（每个全局帧 = 1cs，§5.0）：
     0a. 持续效果/状态恒有：灼烧 0.5s、剧毒/再生 1s 到期即结算（相位固定）
         - 灼烧：X 点伤害（先扣护盾，2 伤/1 盾），结算后层数衰减 20%
         - 剧毒：X 点伤害（无视护盾，不衰减）；再生：恢复 X 点血量
         - 状态（加速/减速/冰冻）与 buff 剩余时长 -= 1cs，归零即移除
     0b. 卡牌行动条推进：gauge += 1cs（整数）；gauge ≥ period 即计入本触发帧的待行动集合
         （period = round(cooldown_cs × cdp ÷ 100 ÷ 速度倍率)，整数；速度倍率 = stats.speed（缺省 1）
          × 加速 2 / 减速 0.5 / 冰冻 0，加速的等效行动间隔最短不低于 1s）
     0c. 触发帧关闭（每 20cs）：本帧累积的事件与触发器进入第 1–3 步结算
  1. gauge 满者执行主动行动（多张同时满 → 按 5.1 优先级规则排序后依次行动）：
     a. 广播 beforeAction
     b. 依次结算主动效果（`abilities` 中 kind: active 的条目按书写顺序依次触发；
        声明 everyN 者仅在本卡第 N 的整数倍次主动行动时结算，按 actionCount 计数）
        **无内置普攻**：任何伤害都必须由这些效果条目显式声明（v0.20 决议）
     c. 按 multicast 次数重复执行整个主动行动（默认 1；>1 的卡面标注 *N）
     d. 广播 afterAction / onAction
     e. 行动产生的伤害事件广播 onPlayerDamaged
  2. drainTriggerStack()：弹出栈顶触发器（含卡牌被动与玩家技能）→ 检查 condition
     → 执行 actions（新事件继续入栈，直到栈空）
  3. 检查胜负：任一方 hp ≤ 0 立即结束；到达 MAX_TICK 判平局，平局判我方胜（规则 §3 v0.8）
```

### 5.0 时间模型：两级颗粒度与整数数值口径（v0.19 立）

#### 5.0.1 两级颗粒度

引擎里只存在**一个真实时间轴**，但以两种颗粒度被观察：

| 颗粒度 | 步长 | 作用范围 | 别名 |
|--------|------|----------|------|
| **全局时钟**（最小帧） | **0.01s**（1 厘秒 = 1cs） | 一切"连续流逝"的量：冷却 / 行动条推进、持续效果（灼烧 · 剧毒 · 再生）的周期、状态（加速 / 减速 / 冰冻）与 buff 的剩余时长、`chg` 充能时长 | 全局 tick / cs |
| **触发器帧**（最小触发帧） | **0.2s**（= 20cs） | 只约束**触发器的结算时机**：被动与技能何时允许被结算、每 tick 的去重与顺延 | tick |

关系：**1 触发帧 = 20 全局帧**。规则 §1"tick 只约束触发器结算时机，持续效果与状态计时按 0.01s 精度流逝"即此意。之所以必须分成两级：若一切都按 0.2s 走，持续效果与状态时长会被 0.2s 网格强行对齐，debuff（0.5s / 1s 周期、短时长）的结算相位会产生累计误差，且 0.5s 无法被 0.2s 整除（0.5 ÷ 0.2 = 2.5），必然出现"有时隔 2 帧、有时隔 3 帧"的抖动。

两级时钟的**执行序**（同一全局帧内，编号即顺序，保证确定性）：

1. **全局帧推进**（`globalTick++`，每帧 1cs）——唯一的真相来源，所有计时量按 cs 增减；
2. 每个全局帧内，按固定相位处理"到期的连续量"：持续效果跳变（周期到 → 结算伤害/回血）、状态与 buff 时长递减（归零 → 移除）；
3. **每 20 个全局帧（即每 20cs）关闭一个触发帧**：把该触发帧内累积的事件与触发器一次性结算，结算顺序按 §5.1 的优先级规则；
4. 结算中产生的新事件，并入**下一个触发帧**的候选（不打断当前帧的排序），即规则 §6.3 的"同一 tick 内多次触发只触发一次、其余顺延到下一个 tick，直到没有积累"。

> **相位（phase）约定**：每个全局帧内"先递减时长、再判定到期"固定不变；触发帧边界固定落在 `globalTick % 20 === 0`。两条都写死，是为了让同一 seed 在任何宿主上跑出逐字节一致的日志。

#### 5.0.2 全局数值一律为整数（v0.19 决议）

**所有数值量都是整数**，包括时间量、伤害/治疗量、护盾、层数、进度。换算与舍入口径：

| 量 | 单位 | 说明 |
|----|------|------|
| 时间量（冷却、周期、时长、充能） | **cs（整数）** | YAML 里仍写秒（`cooldown: 1.5`），进引擎即换算为 `1.5 × 100 = 150cs`；YAML 允许两位小数，故换算后必为整数 |
| 行动条进度 gauge | **cs（整数）** | `gauge += 1` / 全局帧；`gauge ≥ period` 时充满并执行主动行动，执行后 `gauge -= period`（余量结转，不丢精度） |
| 伤害 / 治疗 / 护盾 | 整数 | 施加时即为整数；「1 盾抵 2 点灼烧伤害」换算后的护盾消耗也取整 |
| 层数 / `stackLimit` / `everyN` / `actionCount` | 整数 | 计数类天然整数 |
| 优先级 | 整数 1–10 | 缺省 5 |

**舍入规则（分两类，不要混用）**：

- **单次中间结果**：出现小数就把**这一次运算的结果**四舍五入到整数，随后按整数参与后续运算（不是"全程保留小数、最后才取整"）。
  - 例：`period = round(cooldown_cs × cdp ÷ 100 ÷ 速度倍率)`——`cdp` 与速度倍率可产生小数，故在此取整；取整后 `period` 是整数，后续全是整数加法。
  - 例：灼烧衰减 `stacks - stacks × 0.2`：先算 `round(stacks × 0.2)` 得到整数衰减量再相减。
- **累积型百分比衰减（唯一例外）**：灼烧层数的 `-20%/跳` 属"自己乘自己"的指数衰减，若每跳都取整会过早衰减到 0（1 层 × 0.8 = 0.8 → round 成 1 → 永远衰减不掉）。故**层数在内部保留小数参与累积、只在对外读取（伤害计算、日志、界面、条件比较）时取整**，并以规则 §18.3 的"层数 < 0.01 视为清除"作为终止条件。
  - 这是整数口径的**唯一豁免**，且豁免范围只限"灼烧层数这一个内部累加器"，其对外表现仍是整数。

**推论**：

- 引擎内部**只做整数加减**（上述豁免除外），不做浮点累加，故不会出现 `0.1 + 0.2 = 0.30000000000000004` 这类跨平台差异；
- 所有"百分比"（`cdp`、灼烧衰减、治疗净化 5%、`hpPct` 条件）都在**用到它的那一次运算**里取整，不在源头改写配置数据；
- 日志与界面展示的数值与引擎内部值**完全一致**（因为内部已是整数），不需要"显示时再修一次"。

### 5.1 触发结算优先级与节流（规则 §5、§6.2/6.3）

**优先级（被动与技能同台比较）**：

1. 所有效果（主动、被动、技能）自带 `priority` 字段，**数值大者优先**；
2. 优先级相同，**加载早者优先**：战斗开始时按"先本方、后敌方，每方从左到右"加载场上卡牌，加载顺序即入场顺序；
3. 行动阶段多张卡同时满足行动条件时，同用第 1、2 条。

**主动效果通道**（不走被动优先级比较）：行动条充满即随主动行动按书写顺序结算；多张卡同时充满时按第 1、2 条排序，单卡内效果队列按书写顺序依次结算。技能无冷却，不走主动通道。

**技能 vs 卡牌被动**：技能无入场时间，使用默认 `priority`；优先级相同时技能视为加载顺序最低，**技能后于卡牌被动结算**（规则 §6.2 / §12 v0.8 决议）。技能携带数量无上限。

**触发节流（规则 §6.3）**：触发器条件发生后 0.01s 尝试触发效果；**每个触发器每 tick 最多结算一次**，同一 tick 内多次满足的次数积累到下一 tick（逐 tick 清空，直至没有积累），以 `queuedTriggers` 计数。

```yaml
size: medium            # small=1格 medium=2格 large=3格，可 slots: N 覆盖
rarity: gold            # 品阶 id = 最低品质
stats: { atk: 45 }      # speed 行动条速度倍率缺省 1，一般不修改
tags: [野兽, 火系]

abilities:
  - kind: passive
    priority: 10              # 被动触发优先级（缺省 5，范围 1–10）
    trigger: { event: onPlayerDamaged }   # 玩家受伤时（敌我均广播，见《时机表.md》）
    condition: { cmp: eq, left: { var: player }, right: { ref: enemyPlayer } }   # 仅敌方玩家受伤
    actions:
      - do: gainStat
        stat: atk
        amount: { mul: [self.atk, 0.2] }
        stackLimit: 5

  - kind: active              # 主动效果：挂靠在本卡唯一的行动条上，充满即按书写顺序触发
    everyN: 3                 # 选填：仅每第 3 次主动行动时结算（缺省每次充满都结算）
    actions:
      - do: dealDamage
        target: { pick: randomEnemyCard }
        amount: 80
```

### 6.2 条件与数值表达式（L2 显式写）

```typescript
type Condition =
  | { cmp: 'lt' | 'lte' | 'gt' | 'gte' | 'eq' | 'neq', left: Expr, right: Expr }
  | { not: Condition } | { any: Condition[] } | { all: Condition[] };

type Expr =
  | number
  | { ref: 'self.atk' | 'self.speed' | 'enemyPlayer.hp' | 'ownPlayer.hp'
           | 'ownPlayer.hpPct' | 'cardsOnBoard' | ... }   // 封闭引用表
  | { count: Selector }
  | { add: Expr[] } | { sub: Expr[] } | { mul: Expr[] } | { div: [Expr, Expr] };
```

**效果数值书写规则（规则 §8.2）**：`abilities` / `enchant` 内数值型参数（`amount` / `seconds` / `duration` 等）禁止字面量，必须引用本卡 `stats` 字段；`{ ref: self.<stat> }` 可简写为裸字符串（`amount: self.atk` 等价于 `amount: { ref: self.atk }`）。字面量只允许出现在表达式内部（系数 / 阈值）与结构性参数（`everyN` / `stackLimit` / `priority` / condition 阈值）。

### 6.3 技能 YAML 格式

```yaml
# skills/ember_oath.yml
id: ember_oath
name: 烬火誓约
version: 1
icon: ember_oath_circle    # 可选，头像两侧的圆形图标
priority: 8                 # 与卡牌被动同台比较的优先级（缺省 5，范围 1–10）

stats:                       # 开放数值表（v0.10 新增）：技能效果数值唯一来源
  shd: 100                   # 护盾数值
  atk_boost: 10              # 攻击增益数值

trigger: { event: onPlayerDamaged }     # 玩家受伤时（敌我均广播）
condition:
  all:
    - { cmp: eq, left: { var: player }, right: { ref: ownPlayer } }        # 仅己方玩家
    - { cmp: lt, left: { ref: ownPlayer.hpPct }, right: 0.3 }              # 血量低于30%
actions:
  - do: shield
    target: ownPlayer
    amount: self.shd                      # 引用本技能 stats（v0.10：技能自带 stats，禁止字面量）
  - do: gainStat
    stat: atk
    amount: self.atk_boost
    target: { pick: allOwnCards }          # 全体己方卡牌
```

技能与卡牌共用第 7 节动作原语与第 8 节时机词表；不支持的字段（卡牌专属字段如 everyN）在校验阶段直接拒绝并提示。

## 7. 动作原语（规则说明书 §9）

**第一版最小集合 8 个**，语义、参数、边界以《规则说明书》§9 为准（此处为实现侧摘要）：

| 动作 | 说明 | 关键参数 | 边界要点（规则 §9） |
|------|------|----------|------|
| `dealDamage` | 造成伤害 | target（玩家或卡牌选择器）, amount | 作用于玩家：实际伤害 = `min(amount, 可承受量)`，溢出丢弃、不产生额外事件；先护盾后血量（普通 1 盾抵 1 伤，灼烧 1 盾抵 2 伤，剧毒无视护盾）；广播 onPlayerDamaged。作用于卡牌：无血量、无实际损失，仅广播 onCardDamaged 供"受伤"类联动 |
| `healPlayer` | 治疗玩家 | target, amount | 不超 maxHp；X 点治疗清除 0.05X 层灼烧与 0.05X 层剧毒（净化在回血之后结算）；满血时恢复量为 0 仍结算净化并广播 onPlayerHealed |
| `gainStat` | 属性增减（以 buff 挂目标） | stat, amount（支持负数）, duration?, stackLimit?, target | 到期于 tick 边界移除；达 stackLimit 后替换同 stat、同 source 最早一层并刷新时长；同属性多 buff 线性相加，乘算类不支持（需扩展时按 §6 流程增补） |
| `shield` | 附加护盾 | target, amount, duration? | 合并为单一护盾池、总额累加，默认永久；消耗顺序与获得顺序无关；抵御灼烧（2 伤/1 盾）不防剧毒【是否改多盾条分别计时，待定，见第 13 节】 |
| `applyStatus` | 施加卡牌状态 | target, status（`haste / slow / freeze`）, duration（必填） | 三种状态互斥，后施加覆盖先施加；加速 ×2（等效行动间隔最短不低于 1s）、减速 ÷2、冰冻速度为 0 且不能主动行动；到期 tick 边界移除；对 destroyed 卡静默跳过并记 warn 日志 |
| `charge` | 行动条充能 | target, seconds | 单次推进最多触发一次主动行动（gauge 溢出保留，不连锁第二次）；对 destroyed / freeze 卡静默跳过并记 warn 日志 |
| `destroy` | 使卡牌失效 | target | 失效 ≠ 离场：卡牌仍占位，不推进 gauge、不主动行动、被动停用，buff/debuff 数据保留；目标不存在或已失效时静默跳过记 warn；触发 onCardDestroyed |
| `repair` | 修复失效卡牌 | target | 移除 destroyed 标记，gauge 从 0 重计，保留的 buff/debuff 立即恢复生效；目标未失效时静默跳过记 warn；触发 onCardRepaired |

**持续效果不是卡面动作原语**：灼烧 / 剧毒 / 再生由引擎内置周期触发器实现（规则 §18.3–18.5，内部时机词 `onBurnTick` / `onPoisonTick` / `onRegenTick`），卡面不直接书写施加它们的动作；加速 / 减速 / 冰冻经 `applyStatus` 施加。

**原则**：写真实卡牌时发现表达不了的句式 → 记录失败样例 → 优先补原语。新增原语按 §6 流程（见 AGENT.md §6）同步四处文档并补测试。

逃生舱 `{ do: 'script', lang: 'lua', code: '...' }` **禁止实现**（本方案明确不建议，AGENT.md §6 重申）。

## 8. 触发时机词表

> 词表已拆分为独立文件《时机表.md》维护（规则说明书 §7），实现以《时机表.md》为准，两边保持同步。要点：

- **封闭词典**：解析失败即报错并给出最接近的合法词条建议；
- **无召唤设定（v0.4）**：游戏内不存在召唤物，所有卡牌战斗前一次性布置，无进场/退场时机；卡牌失效走 `onCardDestroyed`、复原走 `onCardRepaired`；
- 卡牌"受伤"类联动走 `onCardDamaged`（`dealDamage` 指定卡牌时广播，卡牌无实际损失）；
- 主动效果没有触发时机词：挂靠在本卡唯一的行动条上，充满即随主动行动按书写顺序结算（`everyN` 按 actionCount 计数）；
- 高频时机（`beforeAction` / `afterAction` / `everyN`）开放给技能，与卡牌同等受单 tick 去重约束（v0.11 决议）；状态类时机（`onCardFrozen` / `onCardHasted` / `onCardSlowed` / `onCardCharged`）已落定开放；`onTickStart` / `onTickEnd` 已移除。
