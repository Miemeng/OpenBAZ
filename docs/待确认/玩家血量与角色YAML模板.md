# ============================================================
# 一、血量归属：为什么是"角色设定"而不是卡包或阵容？
# ============================================================
#
# 三个候选位置：
#
#   A. packs/<pack_id>/pack.yml          ❌ 否。血量是**玩家/角色**的属性，不是卡包属性的。
#                                          卡包是卡牌集合，多个不同角色会共用同一个卡包；
#                                          写进卡包会导致"同一卡包只能有一种血量"。
#
#   B. decks/*.yml（阵容文件）            ⚠️ 半对。阵容确实**携带**血量（模拟模式设计文档 §4.3
#                                          "双方血量由摆盘界面配置"），但它是"本局采用哪个角色的
#                                          什么血量"，属于**引用与覆盖**，不是血量的定义处。
#                                          把定义写在阵容里，等于每建一个新阵容都要重填一遍血量，
#                                          且同一角色在不同阵容里血量可能不一致，无法收敛平衡。
#
#   C. 角色设定文件（本草案）              ✅ 是。血量是角色的**基础设定**，与角色的技能组、
#                                          初始护盾、成长曲线同源；阵容只引用角色 id，可选择性覆盖。
#
# 结论：**定义在角色文件，阵容引用、引擎读取**。
#   规则 §2 的"血量"行、§3 的胜负规则（hp ≤ 0）都不需要改——变的只是"这个 hp 从哪来"。
#
# 与现有实现的关系：
#   [engine/state.ts](../engine/state.ts) 里的 `INITIAL_HP = 300` 是**过渡常量**，
#   已带 TODO 注释；角色文件落地后，`createBattleState` 改为从 `BattleOptions.players[side].hero`
#   取 `maxHp`，该常量退化为"角色文件缺失时的兜底值"或直接删除。
#

# 三、阵容文件引用方式（decks/*.yml 草案，与模拟模式设计文档 §4.3 对齐）
# ============================================================
#
# 阵容用 `hero` 引用角色设定，并可**选择性覆盖**血量（用于模拟模式"双方血量"输入框）：

# id: deck_a
# name: 我方测试阵容
# hero: hero_vanguard            # 引用 heroes/<id>.yml；血量取该角色的 hp
# overrides:                     # 选填：本局临时覆盖（模拟模式摆盘界面填的血量走这里）
#   hp: 300
# placements:                    # 摆盘：卡牌 id + 左端所在格（1–10）
#   - { card: cinder_wolf, slot: 1 }
#   - { card: iron_guard, slot: 3 }
#   - { card: ember_priest, slot: 7 }
# skills: [ember_oath, second_wind]

# 说明：
#   - `placements[].slot` 是**左端格号**（1–10），占格数由卡牌的 size / slots 推导；
#   - 同名卡可多张（规则 §2），引擎自动生成不同 instanceId（`<side>-<cardId>-<slot>`），
#     故阵容文件里不需要写 instanceId；
#   - 摆盘合法性由 `engine/board.ts` 的 `validatePlacements` 统一校验，
#     客户端与 CLI 调用**同一个函数**（API文档 §2.3：客户端不自行实现规则）。
